# 문서 기반 개발 흐름

## 현재 범위

기본 실행 기반의 명세·계획은 사용자 승인을 받았으며 구현·검증을 완료했다. 이미 수행한 단계를 전체 workflow로 중복 실행하지 않는다. 현재 상태는 [진행 상태](progress.md)를 따른다.

## 진행 순서

1. 기획 대화의 결정·미정을 즉시 docs에 기록한다. PPTX는 원본 근거로 남긴다.
2. `$speckit-specify`와 필요한 `$speckit-clarify`로 기준 docs·요청 범위·진행 근거·문서 영향을 포함한 명세를 작성한다.
3. `$speckit-plan`으로 기술 선택·문서 갱신·검증을 계획한다.
   - 명세·계획의 링크, 핵심 동작·제외 범위·기술적 가정·검증 방법을 제시하고 요청된 작업을 계속한다. 별도 승인 대기는 두지 않으며 실제 사용자 승인을 받은 것처럼 표시하지 않는다.
4. `$speckit-tasks`로 실제 작업을 만든다. docs 갱신·verification 작성·진행 기록은 필수다.
5. `$speckit-analyze`로 모순·누락을 점검하고 중요한 미정을 해결한다.
6. 요청된 범위 안에서 `$speckit-implement`로 최소 실행 가능한 틀·기본 기능부터 만들고 작게 확장한다.
7. 각 증분을 검증하고 docs·기능별 verification.md를 갱신한 뒤 관련 변경을 커밋한다.
8. `$speckit-converge`가 남긴 작업이 있으면 같은 흐름에서 구현·검증·문서 갱신·커밋을 반복한다. 다음 증분마다 진행 승인을 기다리지 않는다.

Codex가 순서를 안내한다. 직접 스킬을 호출해도 AGENTS·constitution·프로젝트 템플릿 규칙이 적용된다.

## 점진적 개발과 Git

- 독립적인 기능 개발에는 `feature/<기능명>` 브랜치를 생성하거나 같은 기능의 기존 브랜치를 사용한다. 단순 문서·지침 갱신, 색상 점검·명암 복원 같은 소규모 보정에는 새 브랜치를 만들지 않고 현재 브랜치에서 처리한다. 시작 전에 브랜치와 미커밋 변경을 확인한다.
- tasks를 최소 실행 가능한 틀 → 기본 동작 → 필요한 확장 순으로 나눈다. 각 단위에 관찰 가능한 결과·검증·문서 갱신·커밋 지점을 포함한다. 빈 틀만 만든 것을 기능 완료로 표시하지 않는다.
- 기능 전체 완성 전에 작고 일관된 단위로 커밋한다. 해당 증분의 코드·테스트·docs·specs·검증을 함께 담고 변경 이유와 실제 검증 결과를 메시지에 적는다.
- 기존 사용자 변경은 보존하고 무관한 변경을 일괄 stage하거나 커밋하지 않는다. 같은 파일에 섞인 변경은 diff를 확인해 분리하며 안전하게 분리할 수 없으면 그 이유를 기록하고 나머지 작업을 계속한다.
- 동시 쓰기 작업은 독립 워크트리를 권장한다. 사용 가능한 `create_worktree`로 만들고 각 작업의 브랜치·담당 파일을 정한다. 읽기 전용 검토에는 별도 워크트리가 필요하지 않다. 같은 파일을 두 에이전트가 동시에 수정하지 않는다.
- PR 생성·게시·병합 단계에서만 진행 승인을 받는다. 먼저 변경·검증·PR 제목/본문을 준비하여 검토 가능하게 만들고 이미 받은 승인은 반복해서 묻지 않는다. 일반 개발·로컬 커밋은 계속한다.
- 정보 부족 질문은 승인 요청과 구분한다. 요청 밖의 게임 기획·기능을 임의로 추가하지 않으며, 명시적 보류는 유지한다. 실행 환경 자체의 권한 제한은 이 규칙으로 해제되지 않는다.

## 서브에이전트와 모델 선택

독립 탐색·검증·구현은 효과가 있을 때 위임하고, 단일 작은 수정은 직접 수행한다. 주 에이전트가 통합·결과 검토·최종 검증을 맡는다. 목표, 관련 파일과 기준 문서, 담당 범위, 금지 사항, 수용 기준, 반환 형식을 명확히 전달한다.

아래는 2026-11-10 [OpenAI 공식 Subagents 안내](https://learn.chatgpt.com/docs/agent-configuration/subagents)와 [Model selection 안내](https://developers.openai.com/api/docs/guides/model-selection)를 현재 호출 가능한 모델에 적용한 프로젝트 시작값이다. 공식 고정 배정표나 성능 보증이 아니며 난도·지시의 구체성·실패 비용·검증 결과에 따라 조정한다.

| 작업 성격 | 모델 | 추론 수준 시작값 |
|---|---|---|
| 명확한 경로·수용 기준이 있는 탐색, 단순 수정, 제한된 문서 점검 | `gpt-6-luna` | `low` 또는 `medium`; 복잡한 논리 검토는 `high` |
| 여러 파일의 구현·테스트, 단계 간 의존성이 있는 일반 개발 | `gpt-6.1-sol` | `medium`; 원인 추적·경계 조건이 많으면 `high` |
| 모호하거나 상충하는 근거, 어려운 설계·분석, 높은 실패 비용 | `gpt-6-astra` | `medium`; 특히 어려운 경우 `high` 또는 `xhigh` |
| 화면 중심 검증·컴퓨터 조작, 범위가 명확한 시각적 수정 | `gpt-6.1-terra` | `medium`; 결과 검증 난도에 따라 조정 |

- 공식 안내의 시작점은 Codex 일반 작업에 Sol, 가벼운 작업에 Luna다. 모델과 추론 수준은 별도 선택이며 항상 최고 수준을 쓰지 않는다. 같은 수용 기준으로 결과를 확인하고 부족하면 지시를 구체화하거나 수준/모델을 올린다.
- 매 호출 시 실제 도구가 지원하는 모델·추론 수준을 확인한다. 지원하지 않는 이름을 만들어 쓰거나 설정 변경 성공을 추정하지 않는다.
- 현재 `spawn_agent`에서는 모델/추론 수준을 지정할 때 `fork_turns="none"`을 사용하고 필요한 맥락을 직접 전달한다. 전체 이력을 상속하는 호출은 부모 설정을 따른다. 이 제약은 도구 계약이 바뀌면 재확인한다.
- 위임할 때 선택한 모델·추론 수준과 이유를 짧게 알린다. 실패·미검증 결과를 통과로 취급하지 않는다. 전역 설정을 고정 변경하기보다 작업별 호출에서 선택한다.

## 기록과 완료

- docs는 현재 승인 설계와 구현 상태, specs는 진행 중인 변경의 작업 문서다. 변경 경위는 Git 로그·diff로 확인하며 별도 연표를 누적하지 않는다.
- 사용자 결정·기술적 가정·작업 진행·구현 완료를 구분한다. 요청 범위 안의 명세·계획은 별도 승인 없이 Ready로 진행할 수 있다. Approved는 실제 사용자 승인 근거가 있을 때만 표시한다. 코드나 커밋의 존재만으로 구현 완료를 주장하지 않는다.
- verification에는 요구사항별 실제 명령·결과·미실행/실패·문서 갱신·남은 문제를 기록한다.
- 문서 영향이 없으면 이유를 적는다. 날짜 변경만으로 갱신을 대신하지 않는다.
- 자동 테스트·Pico2D 실제 창/입력·사람의 플레이 판단은 서로 대체되지 않는다.
- progress와 verification은 현재 상태·최신 유효 결과로 갱신한다. 폐기된 규칙과 해결된 질문을 지운다. 현재 선택 이유와 미해결 위험은 남긴다.
- 완료 specs는 docs 반영·검증 결과의 커밋 보존·참조 없음이 확인되면 후속 정리 변경에서 제거할 수 있다. 미커밋 근거를 먼저 삭제하지 않는다. 커밋은 검증된 증분마다 수행한다.

## 설정 위치

- .specify/memory/constitution.md: 공통 원칙.
- .specify/templates/overrides/: spec/plan/tasks/checklist 템플릿. 기본 파일은 직접 수정하지 않는다.
- .specify/workflows/overlays/speckit/circuit-warden-docs.yml: 공식 speckit 흐름에 docs 작성·갱신, analyze, converge를 포함.
- AGENTS.md: 읽기 순서·요청 범위·역할·점진적 개발·위임·도구 경로.

CLI 단계 실행 완료가 게임 완성 보증은 아니다. converge가 남긴 작업·미실행 테스트·문서 불일치가 있으면 완료가 아니다. 스킬과 CLI 흐름을 동시에 중복 실행하지 않는다.
